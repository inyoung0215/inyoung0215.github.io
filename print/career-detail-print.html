그라파나 관측 스택 도입 · 신규 구축 — 로그만 있던 환경에 통합 모니터링 도입

2026.08—

팀 내 서비스 클러스터에 통합 모니터링 시스템이 부재하여, 오류 발생 시 각 컨테이너의 로그를 개별적으로 확인해야만 상태를 파악할 수 있었습니다. 늘어나는 서비스 환경에서 운영 비효율을 해결하고자 관측(Observability) 스택 도입을 제안하고 구축하였습니다.

문제 상황
  • 팀 내에 통합 모니터링 시스템 부재 → 로그 조회 외 서비스 상태 파악 불가
  • 서비스 오류 발생 시 각 컨테이너 로그를 개별 확인해야 해 재현·진단 시간 과다
  • JVM 힙·CPU·스레드·DB Pool 등 실시간 지표 확인 수단 부재
  • 팀 리드가 fleet 전체 상태를 한눈에 볼 수 있는 통합 화면 부재
원인 분석
  • 관측 스택 자체가 없어 진단 수단이 로그 파일 개별 조회로 한정
  • 서비스마다 로그 위치 파편화 → 단일 UI에서 통합 조회 불가
  • 표준화된 라벨·폴더 규약 부재 → 신규 서비스 온보딩 시마다 개별 대응 발생
  • 서비스 트래픽이 낮아 일반적인 RPS 기반 대시보드는 무의미 → 저트래픽 특성을 반영한 지표 설계 필요
  • Docker Swarm은 config 오브젝트 내용 변경 미지원 → 대시보드 무중단 갱신 방식 별도 설계 필요
  • Swarm bind mount는 node-local → 서비스 컨테이너와 수집 에이전트의 동일 노드 배치 전제
해결 과정
  1. 통합 수집 에이전트 채택 (Grafana Alloy)
    • Alloy 하나로 node-exporter · cAdvisor · promtail · Prometheus Agent를 대체해 컨테이너 수와 설정을 단순화
    • mode: global로 모든 Swarm 노드에 배포해 bind mount의 node-local 제약 해결
    • 서비스 식별은 컨테이너 라벨(observability.service)을 단일 진실 원천으로 두고, relabel 우선순위(라벨 → Swarm service → compose service → container name)를 정의
  2. 서비스 자동 온보딩 규약 설계
    • Docker 라벨 4개(observability.*)만 붙이면 Prometheus scrape 자동 등록
    • 폴더 규약을 통해 Loki 자동 수집 (폴더명 fallback + JSON 필드 override)
    • 팀원 누구나 관측 스택 코드를 건드리지 않고 신규 서비스를 온보딩할 수 있도록 가이드 문서화
  3. 하이브리드 배포 · Docker Swarm configs 무중단 갱신 패턴 정립
    • 관측 서버는 Standalone Docker로, 앱 노드들은 Swarm 클러스터로 운영하는 하이브리드 배포 구조 설계 → Alloy가 Swarm 경계를 넘어 관측 서버의 Nginx 게이트웨이로 push하도록 구성
    • Swarm이 config 내용 변경을 지원하지 않는 제약 → STACK_CONFIG_VERSION 환경변수로 config 이름에 버전 suffix 부여
    • 값을 1→2→3 올리면 새 config 생성 후 서비스 자동 갱신, 스택 삭제·재배포 없이 대시보드 업데이트
  4. 트러블슈팅 중심 대시보드 3종 구성
    • 초안 5개를 Overview(홈) · Application Runtime · Application Logs 3개로 압축하고, 운영·진단에 필요한 지표만 선별해 패널을 직접 배치
    • Application Runtime에 HTTP 요청·응답과 DB Pool(HikariCP)을 통합 → “느린 API 원인이 DB 대기인가”를 한 화면에서 판단
    • 저트래픽 환경에 맞춰 RPS 대신 분당 요청 건수로 전환. 패널마다 집계 방식(단일 창 외삽 vs 서브쿼리 vs Grafana step 기반)이 달라 같은 요청 수가 어긋나던 정합성 문제를 서브쿼리 방식으로 통일해 세 패널 모두 일치하도록 조정
    • 표의 서비스명·URI를 클릭하면 필터와 시간 범위가 이어진 채 로그 대시보드로 넘어가는 드릴다운 구성

배운 점

관측 스택을 구축하며 가장 크게 배운 것은 도구를 붙이는 일보다 “무엇을 볼 것인가”를 정의하는 일이 훨씬 어렵다는 사실이었습니다. Grafana·Prometheus·Loki 같은 도구는 문서만 따라가면 붙일 수 있지만, 우리 팀이 실제로 필요한 지표—어떤 시점에 무엇을 확인해야 오류를 좁힐 수 있는지—를 정의하는 데 훨씬 많은 시간이 들었습니다. 관측의 시작은 도구가 아니라 “답을 찾기 위한 질문을 먼저 정의하는 일”이라는 것을 이 프로젝트에서 확실히 배웠습니다.

롯데카드 협업 체크인서울 선불카드 서비스 구축 — 외부 카드사 연동과 응답 통보 체계 설계

2026.05—07

롯데카드와 공동으로 외국인 관광객 대상 선불카드 서비스를 신규 구축했습니다. 선불카드(발급·충전·인출·활성화) 전 흐름의 백엔드를 담당했으며, 카드사 규격 준수와 정산 대사가 성립하는 응답 통보 체계가 요구사항의 핵심이었습니다. (정산 대사 로직 자체는 카드사·별도 시스템 소유) API 29개 · 카드사 결과코드 51종 · 도메인 에러코드 65종 · 테스트 156케이스(4,400여 줄) 규모의 백엔드를 설계·구현·테스트했습니다.

문제 상황
  • 정산 대사 성립 조건 미충족 위험: 키오스크는 고객이 언제든 이탈할 수 있는데, 카드사 정산 대사는 거래 시작과 종료 코드가 1:1로 맞아야 성립 → 이탈 1건이 곧 대사 시스템에서 불일치로 표시
  • Redis 장애 리스크: 보안 규약상 민감한 여권·회원 정보를 RDB에 영구 저장할 수 없어 Redis 의존도가 높으나, 장애 시 거래 세션이 유실되는 구조
  • 중복 충전 위험: 카드사 API 통신 오류 대응 로직이 호출 지점마다 흩어져 있어 비즈니스 오류까지 재시도될 위험 상존
원인 분석
  • 예외 발생 시 거래 트랜잭션과 함께 종료 코드 전송까지 롤백되어 카드사에는 시작만 남는 현상 발생
  • 화면 단위의 이탈·타임아웃 지점이 제각각인데 이를 카드사 코드 체계로 매핑하는 표준 부재
  • 재시도 대상을 선별하지 않아 통신 장애 외에 비즈니스 예외까지 재전송되어 중복 충전 유발
  • Redis를 세션 저장소로 쓰면서 하드웨어/네트워크 장애 시 대체 경로 부재
대안 검토
  • 모든 통신 실패에 대해 재시도하는 단순 방식 — 재시도 대상을 선별하지 않으면 비즈니스 예외까지 재전송되어 재시도가 곧 중복 승인이 됨 → 통신 오류 2종만 허용하고 차수 정보를 전달해 상대 기관이 중복을 식별할 수 있도록 하는 방향으로 재설계
  • 단일 트랜잭션으로 거래·통보를 함께 처리하는 방식 — 내부 예외로 트랜잭션이 롤백되면 종료 코드 전송까지 롤백되어 대사 불일치 유발 → AFTER_COMPLETION + REQUIRES_NEW로 트랜잭션을 분리하는 방향으로 결정
해결 과정
  1. 응답 통보 보장 설계 — “어떤 경우에도 종료 코드는 전송된다”
    • 화면 단위 이탈 지점을 전수 조사해 거래중단 코드 14종을 정의하고, 하드웨어 장애·한도 초과 등을 포함한 결과코드 51종 체계 정립
    • 내부 에러코드 ↔ 카드사 결과코드 양방향 매핑 테이블을 구성하고, 미분류 예외는 D999로 폴백시켜 종료 코드 누락 경로 원천 차단
    • 종료 코드 전송을 @TransactionalEventListener(AFTER_COMPLETION) + REQUIRES_NEW로 분리하여 거래가 롤백되어도 카드사 통보는 보장
    • 전송 결과를 이탈 추적 테이블에 적재해 사후 대사 검증 체계 마련
  2. 외부 통신 재시도 표준화 — 중복 충전 차단
    • 흩어져 있던 예외 처리를 RetryableCallExecutor / RetryExecutor로 일원화하고 도메인별 카운터를 Redis로 격리 관리
    • 재시도 대상을 통신 계층 오류(연결 실패·타임아웃) 2종으로만 한정하고 비즈니스 오류는 즉시 실패시켜 중복 충전 리스크 원천 차단
    • 카드사 규격에 맞춰 재시도 차수를 요청에 실어 전송하고, 차수에 따라 응답 코드를 단계화하여 불필요한 운영 알림 방지
  3. DurableCache — Redis 장애 방어 캐시 계층
    • Redis 1차, DB 2차의 폴백형 캐시를 제네릭 추상 클래스로 설계하여, Redis 실패 시 DB 자동 폴백 및 캐시 재적재 수행
    • 보안 규약을 만족시키기 위해 폴백 저장소를 컬럼 단위 암호화 + 만료 일시 기반 유효성 필터(TTL 기반 임시 저장소)로 설계
    • 잔여 TTL을 보존하는 Read-Modify-Write API를 제공해 거래 도중 값 갱신이 세션 만료 시각을 밀지 않도록 생명주기 통제
    • 자식 클래스가 ttl / type / key 3개만 구현하면 되도록 추상화하여 체크인서울 외 환율·본인인증 도메인에 재사용

배운 점

정합성이 중요한 도메인에서는 데이터가 지나는 경로마다 실패 시나리오를 함께 설계해야 합니다. 이 프로젝트에서 안정성을 가른 것도 정상 흐름이 아니라 이탈·타임아웃 같은 예외 경로를 얼마나 빠짐없이 코드 체계로 고정했는가였습니다. 특히 “무엇을 재시도하면 안 되는가”를 정의하는 일이 재시도 로직 자체보다 중요하다는 것을 배웠습니다. 통신 오류와 비즈니스 오류를 구분하지 않았다면 재시도가 곧 중복 충전이 되었을 것입니다. 또한 외부에 알려야 할 사실은 거래 트랜잭션과 생명주기를 분리해야 한다는 것도 이번에 체감했습니다.

OTA 연동 카드 수령 서비스 구축 — 롤백 불가능한 물리 방출의 중복 방지

2026.01—02

해외 OTA(온라인 여행사)가 사전 발행한 교통·선불카드를 국내 무인 키오스크에서 QR로 수령하는 신규 서비스입니다. 카드 방출은 하드웨어 제어라 소프트웨어적 롤백이 불가능하므로, 중복 수령 1건이 곧 실물 자산 손실과 정산 오류로 직결되는 높은 도메인 정합성이 요구되었습니다.

문제 상황
  • 중복 수령 위험: 수령 흐름이 ‘수령 가능 판별 → 수령 확정 → 카드 방출’ 3단계로 분리되어, 방출 지연 중 사용자가 재시도하면 동일 QR이 두 번 방출될 수 있는 구조
  • 정산 불일치: 방출기·네트워크 장애로 방출 결과가 서버에 도달하지 않으면 거래가 미확정 상태로 영구 잔류 → 실물은 나갔으나 원장은 없는 불일치 발생
  • B2B 정산 한계: 파트너별 계약 단가와 수수료가 달라, 기존 B2C 판매 원장 모델로는 정산 표현이 불가능
원인 분석
  • 단계마다 상태를 거쳐 가지만 단계 간 공통 선점 수단이 부재하여 각 단계가 독립 실행되며 중복 진입 가능
  • 방출은 취소가 불가능하므로, 결과 도착 전에 상태를 확정하면 되돌릴 방법이 부재
  • 기존 투입 금액 기반의 판매 원장 스키마가 계약 단가 및 수수료 기반의 B2B 정산을 수용하지 못함
해결 과정
  1. 신규 도메인 단독 설계
    • 신규 테이블 4개(상품·계약·방출이력·수령확정) 설계 및 기존 거래 원장 2개 확장
    • 도메인 전용 에러코드 대역(20000~20007) 정의 및 Swagger 자동 예시 노출로 단말기 팀과의 규격 조율 효율화
  2. 4계층 중복 수령 방어 설계 (핵심)
    • “락을 어디에 거느냐”보다 “어느 범위를 하나의 단위로 묶느냐”에 집중하여, 성능과 안전성을 모두 잡는 4계층 방어 체계 구축
    • 1계층 (Redis 진행 플래그, TTL 24h): 사용자의 단순 재스캔·재요청 차단
    • 2계층 (Redisson 분산락, 수령 확정 지점): 멀티 인스턴스 환경의 동시 진입 직렬화 (락 점유 시간 최소화를 위해 확정 지점 한 곳에만 적용, wait 3s / lease 5s, fail-fast)
    • 3계층 (거래 컨텍스트 스냅샷 동등성 검증): 단말기 및 조건 변조 여부 검증
    • 4계층 (tb_agency_product_confirm.product_no UNIQUE): 최종 물리 방어선
  3. 2-Phase 방출 프로토콜 + 장애 복구 경로
    • 방출 직전 방출 이력을 PENDING으로 선기록하고 releaseId 발급 · 방출 직후 결과에 따라 SUCCESS/FAILED로 확정
    • 상태 전이를 방출 성공 시점까지 지연시켜, 실패 시 원복해야 할 상태 자체가 남지 않는 구조 설계 (별도 보상 트랜잭션 불필요)
    • 방출 확정 직후 지연 큐에 메시지를 발행해, 일정 시간 내 결과가 오지 않은 미확정 거래를 자동 감지·알림
    • 통신 단절 건을 위한 장애 후처리 전용 API 제공 → releaseId 기준으로 거래를 복구하고, 원장에 정상/장애 거래를 플래그로 분기 기록하여 운영자 DB 직접 수정 없이 복구 가능한 체계 정립
  4. 이벤트 발행 안정화 및 B2B 정산 원장 스키마 설계
    • 슬랙·정산 알림을 @TransactionalEventListener(AFTER_COMPLETION)으로 전환하여, 롤백된 거래가 알림으로 새어나가는 문제 원천 차단
    • 투입금 0원 거래에 계약 단가·판매 수수료·카드 정가를 분리 기록하여 파트너별 복합 정산이 가능한 원장 구조 설계

THE-Free 온라인 환전 서비스 구축 — 앱 신청·키오스크 수령 분리 설계와 가상계좌 동시성 장애 해결

2025.09—10

오프라인 키오스크에서만 가능하던 외화 환전을, 앱에서 미리 신청하고 가상계좌로 입금한 뒤 전국 100대 이상 키오스크 중 원하는 곳에서 현금을 수령하는 형태로 확장한 신규 서비스입니다. 앱·키오스크 클라이언트 개발자와 QA를 포함한 5인 프로젝트에서 백엔드 서비스 2개(앱 대외 API·환전 코어)의 설계와 구현을 담당했고, 오픈 이후 발생한 가상계좌 중복 발급 장애의 원인 분석과 해결까지 맡았습니다.

문제 상황
  • 시점과 공간의 분리: 기존 환전은 “결제와 수령이 같은 순간, 같은 장소”라는 전제였으나, 앱 신청 → 가상계좌 입금 → 키오스크 수령으로 시점이 쪼개지며 환율·재고·기한 정책이 모두 미정의 상태로 대두
  • 실물 재고 불일치: 수령 대상이 키오스크 안의 실물 지폐라, 신청 시점에 있던 권종이 수령 시점에는 소진되거나 현금 수송으로 방출함 통화 자체가 교체될 수 있는 위험 상존
  • 일정 압박: 사외 앱 개발사와 연동해야 하므로 서버가 확정한 계약이 곧 앱 일정 · 스펙 확정이 개발보다 선행되어야 하는 제약
  • 가상계좌 중복 발급 장애: 오픈 후 동일 사용자에게 가상계좌가 중복 발급되는 장애 접수 (월 12건 CS) · 실제 입금이 연결되는 계좌라 정산 정합성 직접 위협
원인 분석
  • 기존 환전 로직은 키오스크 단일 채널 전제 → 신청·수령 시점이 분리된 흐름을 담을 상태 모델 부재
  • 환율은 실시간 변동인데 신청·수령 사이 시간차 발생 → 어느 시점 환율을 보장할지 정책 부재
  • 레거시 Java 모듈에 기능 추가 시 기존 거래 코드와 결합도 상승 → 유지보수 비용 증가
  • 가상계좌 발급이 조회 후 생성하는 check-then-act 구조 → 짧은 간격의 동시 요청이 모두 “미발급”으로 판단해 각각 신규 계좌 생성
  • 발급 이력이 히스토리 성격의 테이블로 관리되어 요청 시점에 잠글 만한 고정 키 부재, 단일 서버 synchronized로는 다중 인스턴스 환경 방어 불가
대안 검토
  • 자원(가상계좌 자체)에 락을 거는 방식 — 아직 발급되지 않은 자원이라 잠글 대상이 없음 → 요청 주체(사용자 식별키)로 락 대상을 옮기는 방향으로 재설계
  • 단일 서버 synchronized로 방어하는 방식 — 다중 인스턴스 환경에서 인스턴스 간 상호 배제가 성립하지 않아 무력 → Redisson 분산락으로 확장
  • 기존 환전 서비스에 신청-수령 흐름을 추가하는 방식 — 기존 거래 코드와의 결합도 상승·상태 모델 오염 → 원장 소유 기준으로 서비스 2개 분리(대외 API + 환전 코어)로 결정
해결 과정
  1. 서비스 분리와 상태·기한 정책 수립
    • 서비스 2개 분리: 앱 노출 창구인 대외 API 서버(요청 검증·복호화·다국어 표현·타 도메인 오케스트레이션)와 환전 코어 서버(거래·가상계좌·시재·환불·한도 원장 소유)로 분리하여 기존 Java 레거시와 격리 및 독립 배포 달성
    • 상태 기계 정의: 정상 경로 3단계(미입금 → 미출금 → 출금완료)와 종료 상태 2개(취소·실패)를 정의하고 허용된 전이만 통과하도록 검증
    • 기한 2단계 분리: 입금 기한 30분(남용·환율 노출 최소화)과 출금 기한(입금일 + 2일 자정)으로 분리하고 배치를 통해 일괄 취소 처리
    • 환율 스냅샷 & 30자리 합성 키: 신청 시점 환율을 동결 저장하고, 앱에는 내부 식별자 대신 합성 키를 왕복시켜 환율 구조를 노출하지 않고 스냅샷 유지
  2. 실물 재고 정합성을 위한 3중 검증
    • 신청 시: 키오스크 잔여 시재에서 최소 방출 잔량을 제외한 가용분만 인정하고, 현금 수송 작업 충돌 검사를 추가해 통화 교체 예정인 권종의 신청 사전 차단
    • 입금 직전: 가상계좌사의 사전 조회 시점에 실시간 시재와 진행 중 거래를 대조하여 부족 시 입금 거절. 롤백에서 제외되는 전용 예외를 도입해 트랜잭션 경계 분리
    • 출금 시: 키오스크가 실제 지폐 방출에 성공한 뒤에만 승인 처리하고, 실패 시 메시지 큐(RabbitMQ)로 보상 트랜잭션을 받아 미출금 상태로 복구
  3. 외부 연동 및 개인정보 보호 강화
    • 가상계좌사 콜백 3종(입금 사전조회·수취조회·입금완료)을 수신 계약으로 설계하고 금액 정확 일치만 허용해 정합성 문제 차단
    • 알림은 트랜잭션 커밋 이후 발행되도록 이벤트로 분리해 푸시 실패가 거래를 되돌리지 않도록 격리
    • 개인정보 3중 보호: 앱↔서버 전송 구간 필드 암호화(SEED-CBC) → DB 컬럼 암호화 → API 경로별 로그 마스킹
    • 주민번호·성별에서 파생한 식별키를 도입해 계정을 바꿔도 사람 기준으로 일일 환전 한도가 누적되도록 관리
  4. 가상계좌 중복 발급(동시성) 장애 대응

이즐(eZL) 교통카드 충전·출금 — 되돌릴 수 없는 물리 기록과 서버 상태의 정합성

2025.01—07

키오스크에서 교통카드 충전과 잔액 출금을 지원하기 위해 이즐(eZL) 시스템과 연동한 프로젝트입니다. 서버가 IC칩의 상호 인증 프로토콜(sign1 → sign2 → sign3)을 중계하는 구조로, 카드에 금액이 기록되는 순간 서버는 그것을 되돌릴 수 없다는 점이 모든 설계의 출발점이었습니다. API 11개 · 신규 테이블 3개 · EZL 연동 API 6종 · 테스트 49케이스(14 시나리오 그룹) 규모의 백엔드를 설계·구현·테스트했습니다.

문제 상황
  • 물리 기록 후 통신 단절: 충전은 서버 요청 → 이즐 승인(sign2) → 키오스크의 실물 카드 기록 → 결과 통보(sign3) 순서인데, 카드 기록 이후 단계에서 통신이 끊기면 카드에는 금액이 충전되었으나 서버·이즐은 미확정 상태로 남는 불일치 발생
  • 상태 판정 불가: 키오스크가 카드 잔액 변동 여부 자체를 확인하지 못하는 예외 케이스 존재 (성공도 실패도 아닌 상태)
  • 중복 충전 위험: 재시도 시 이전 요청이 이즐 측에서 이미 성공했을 수 있어 동일 요청 재전송 시 중복 충전 위험 상존
원인 분석
  • 물리 기록은 소프트웨어적 롤백이 불가능한데, 단순 통신 결과만으로 거래 성패를 판정하면 고객이 투입한 현금을 잃는 방향으로 실패 유발
  • 성공·실패 2단 모델로는 “잔액 확인 불가” 상태를 표현할 수 없어 클라이언트가 결과를 임의로 판단하게 되는 구조
  • 재시도가 서버 상태 확인 없이 반복되면 이즐 측의 기존 성공 건과 충돌 발생
대안 검토
  • 통신 결과로 성공·실패를 판정하는 방식 — 카드에는 이미 금액이 기록됐는데 서버는 실패로 처리 → 고객이 카드 잔액과 투입 현금을 모두 잃는 경로가 생겨 기각. 진실을 서버의 통신 결과가 아닌 카드에 기록된 잔액으로 재정의하는 방향이 필요했음
해결 과정
  1. 물리 상태 우선 원칙 — “카드에 기록됐으면 거래는 성공이다”
    • sign3 전송 단계에서 이즐 통신이 실패해도 거래를 승인으로 확정하도록 설계 (이미 카드의 잔액이 증가했으므로 서버 통신 실패를 이유로 실패 처리하면 고객이 금전적 손실을 입기 때문)
    • 단, 요청이 이즐에 전혀 도달하지 않은 연결 실패는 예외로 분리하여 실패 처리
    • 통신 실패 건은 운영 알림으로 기록하고 사후 대사로 정정하는 경로를 별도 구성
  2. 3-state 상태 모델 + 사후 검증 큐
    • 거래 상태를 승인 / 실패 / 불확정(UNKNOWN) 3단으로 정의
    • 키오스크가 카드 잔액 변동을 확인하지 못한 경우 ‘불확정’으로 기록하되, 현금이 이미 투입되었으므로 고객 보호를 우선하여 키오스크 거래는 승인 처리
    • 해당 거래를 사후 검증 대상 메시지로 발행하여 정산 시스템이 대사로 최종 확정하도록 흐름 분리
    • 클라이언트가 결과를 임의 판단하지 않도록 응답 규격을 3단으로 명시
  3. 중복 충전 차단 (3중 방어 체계 구축)
    • 1계층 (DB 조건부 UPDATE / CAS): progress_yn이 N인 경우에만 Y로 갱신하고, 갱신 건수가 0이면 즉시 거부하여 동시·중복 요청 진입 차단 (Redis 없이 DB 원자적 연산 활용, finally에서 확실히 해제)
    • 2계층 (이즐 응답코드 소급 판별): 재시도 요청 시 특정 코드 수신 시 이전 거래가 실제로는 성공한 것으로 판단, 이전 거래를 승인으로 소급 정정하고 재시도 거부
    • 3계층 (거래 원장 복제 및 체이닝): 재시도 시 상태를 되돌리지 않고 거래·충전·환율·투입 원장을 복제해 신규 거래를 생성하고 이전 거래 ID로 체이닝하여 원본 훼손 없이 감사 추적 보존
  4. 전자화폐 규격 원장화 및 정산 로직 구현
    • 이즐 전문 규격(SAM 거래 일련번호, 전자화폐사·발행사 ID, 알고리즘 ID, 서버/클라이언트 서명 등)을 거래 원장 컬럼으로 전면 보관하여 단계별 실패 지점 추적 가능하게 설계
    • 발행사별 정책(충전·환불 가능 여부, 최대 잔액, 환불 한도)을 마스터 테이블로 분리
    • 구간별 출금 수수료 및 절사 로직을 구현하고, 잔액이 최소 방출액+수수료에 미달하면 거래 시작 전에 차단
    • 외화 투입 충전 시 환율 환산액을 서버에서 재계산해 클라이언트 전달값과 대조 후 불일치 시 거래 차단
    • 카드번호 컬럼 단위 암호화 + 원장 내 마스킹/암호화 값 용도별 분리 저장

    • 외부 통신 예외를 재처리 / 알림 / 무시 3종으로 타입 분리하여, 예외 타입 자체가 운영 정책이 되도록 설계
    • 재처리 대상 실패는 재처리 관리 테이블에 시도 횟수와 함께 적재하고, 배치가 자동으로 재승인하도록 구성
    • 배치 재처리에 필요한 인증 토큰과 여권 정보를 Redis에 별도 보관해 원거래 세션 유실과 무관하게 복구 가능하도록 지원
    • 방출 결과를 ‘전액 성공 / 부분 방출 / 전액 실패’로 분기하고, 실패 시 환급사 취소 통보 후 망상취소 처리
    • 운영자용 수동 복구 API 2종(방출 실패 종결 / 방출 성공 및 재처리 실패 승인)을 상비하여 DB 직접 수정 프로세스 완전 제거
    • 알림은 트랜잭션 커밋 이후(@TransactionalEventListener(AFTER_COMPLETION)) 발행하도록 처리해 트랜잭션 롤백 시 오알림 원천 차단
    • 장애 원인을 QA 체크리스트로 환원하고 방출 후처리 시나리오를 개발 단계의 상시 점검 항목으로 절차화
  2. 환급사 확장을 전제로 한 유연한 연동 구조 설계
    • 환급사 정보(한도·정책)와 단말기×환급사 연계(계정·환급취소 가능 여부) 테이블을 분리하여, 신규 환급사 추가 시 스키마 변경 없이 데이터 등록만으로 대응
    • 외부 통신을 3계층(전송 클라이언트 / 환급사 규격 변환 / 도메인 서비스)으로 분리하고 엔드포인트 15종을 코드가 아닌 설정으로 외부화
    • 환급사 응답 코드 40여 개를 서비스 표준 에러코드로 변환하는 매핑 계층을 두어 사용자 노출 메시지 정책 중앙화
    • 환급사 실통신 서버를 도메인 서버와 물리적으로 분리해 프로토콜 경계 명확화
  3. 민감정보 다층 방어 — 팀 내 첫 Redis 도입 및 컨벤션 자산화
    • 여권 정보를 DB 대신 Redis + TTL(여권 24h / 전표 60분)로 임시 보관해 보관 기간 자동 만료 보장
    • DB에는 여권번호·국적·생년월일·성별을 해시한 식별번호만 저장하고, 잔여 개인정보 컬럼은 JPA 컨버터로 자동 암복호화
    • 키오스크와 서버 구간은 SEED 암호화 적용, 외부 통신 로그는 인터셉터에서 민감 필드 자동 마스킹
    • 여권 MRZ 체크디짓 검증 로직을 도입해 스캔 오인식을 서버 진입 시점에 사전 차단

Redis 도입 컨벤션·키 네이밍·TTL 정책을 문서화한 덕분에 이후 팀 프로젝트에서 그대로 재사용될 수 있었습니다.

알림 발송 서비스 통합 — 흩어진 발송 로직의 단일화와 유실 없는 발송 체계 구축

2024 하반기

환전·선불카드·Tax Refund 등 서비스별로 흩어져 있던 알림 발송 로직을 단일 발송 서비스로 통합하고 채널·템플릿·재시도 정책을 표준화한 프로젝트입니다.

문제 상황
  • 중복 구현: 알림 코드가 프로젝트별로 개별 구현되어, 채널이나 문구를 바꾸려면 4개 저장소를 동시에 수정하고 각각 배포해야 하는 비효율 발생
  • 거래 응답 지연: 발송 호출이 거래 트랜잭션에 동기적으로 묶여 있어, 외부 발송사의 응답 지연이 거래 응답 시간에 그대로 전가되는 구조
  • 알림 유실: 발송 실패 시 재처리 경로가 없어 누락 건을 운영자가 수동으로 확인해야 했고, 실패 원인에 대한 로그 가시성 부재
원인 분석
  • 알림 코드가 프로젝트별로 개별 구현 → 채널·문구 변경 시 여러 저장소 동시 수정·배포 필요
  • 발송 호출이 거래 트랜잭션과 동기적으로 결합 → 외부 발송사 지연이 거래 응답 시간에 그대로 전가
  • 발송 실패에 대한 재처리 경로 부재 · 실패 원인 로그 가시성 부재
  • 하드코딩된 문구 구조 → 문구 변경 시 반드시 코드 수정 + 배포 필요
해결 과정
  1. 거래와 발송의 분리 — Transactional Outbox 패턴 적용
    • 거래 서비스가 발송 요청을 거래와 동일한 DB 트랜잭션 안에서 테이블에 적재하고, 별도 워커가 이를 폴링해 발송하도록 아키텍처 분리
    • 메시지 큐 발행 방식도 검토했으나, 거래 커밋과 큐 발행은 원자적으로 묶이지 않는 한계 직면 (거래는 성공했으나 발행이 실패하면 알림이 영구 누락되거나 반대의 경우 성립하지 않은 거래 알림이 발송되는 위험 발생)
    • 금융 거래 도메인의 특성을 고려하여 ‘유실 없는 발송 보장’을 위해 초 단위의 발송 지연을 감수하는 트레이드오프 선택, 외부 발송사 지연을 거래 응답 시간에서 완전히 격리
  2. 채널 확장이 용이한 유연한 발송 구조 설계
    • 발송 인터페이스를 추상화하고 채널별 구현체를 전략 패턴으로 분리해, 스프링 DI로 런타임에 동적 선택되도록 구성
    • 신규 채널 추가 시 기존 코드를 수정하지 않고 새로운 구현체만 추가하면 되는 확장성 확보
  3. 알림톡 도달률 보장 — LMS 자동 대체 발송
    • 수신 거부나 채널 미연동 등으로 실패율이 존재하는 알림톡의 한계를 극복하기 위해, 템플릿 모델에 대체 템플릿을 1급 속성으로 설계
    • 알림톡 발송 실패 시 동일 내용이 LMS로 자동 대체 발송되도록 구성하고, 알림 유형별 대체 템플릿 강제 검증으로 누락 원천 차단
  4. 자동 재시도 및 실패 격리 체계
    • 발송 건별로 트랜잭션을 독립 분리하여 1건의 실패가 배치 전체를 롤백시키지 않도록 격리
    • 실패 건은 상태와 실패 횟수를 기록해 다음 주기에 자동 재시도하고, 임계 횟수 초과 시 재시도 대상에서 제외해 무한 재발송 방지
    • 실패 사유를 에러 코드로 표준화하여 적재함으로써 원인 분석 소요 시간 대폭 단축
  5. 실시간 장애 가시성 확보
    • 발송 실패 및 템플릿 로드 실패를 Spring Event로 발행하고, RabbitMQ를 통해 Slack에 실시간 통보하는 파이프라인 구축
    • 발송 로직이 알림 인프라를 직접 알지 못하도록 이벤트로 분리하여 통보 채널이 변경되어도 발송 코드는 무영향 유지
  6. 배포 없는 템플릿 운영 체계 (Handlebars 기반)
    • 하드코딩되어 있던 메시지 문구를 템플릿 엔진(Handlebars) 기반으로 외부화하고, 템플릿 CRUD API 및 캐시 갱신 API 제공
    • 코드 수정 및 배포 없이 템플릿 교체 + API 호출만으로 실시간 반영 가능
    • 애플리케이션 기동 시 전체 템플릿을 미리 로드해 콜드스타트를 제거하고, 배치 실행 시에는 필요한 템플릿만 선로딩해 반복 파일 I/O 제거

가장 크게 남은 건 “어떤 안정성을 어떤 비용과 바꿀 것인가”를 명시적으로 결정해야 한다는 점이었습니다. 메시지 큐는 더 세련된 기술처럼 보이지만, 거래 커밋과 발행을 원자적으로 묶을 수 없다는 단 하나의 이유로 이 도메인에는 맞지 않았습니다. 기술의 우열이 아니라 도메인의 실패 비용이 선택 기준이라는 걸 배웠습니다. 또 하나는 정상 경로만 맞춘 설계는 운영에서 반드시 무너진다는 것입니다. 초기 구조에서는 템플릿 파일 로드 실패 한 건이 배치 전체를 멈출 수 있었습니다. 건별 트랜잭션 격리와 실패 횟수 기반 자동 차단, 실시간 장애 통보까지 갖추고 나서야 비로소 믿고 맡길 수 있는 발송 채널이 되었습니다.
